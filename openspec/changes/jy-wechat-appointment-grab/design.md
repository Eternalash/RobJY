## Context

仓库 `RobJY` 目前几乎为空，目标是为上海第九人民医院微信公众号（齐脉 H5：`h5.shqmxx.com`，CustomerId=94）实现可配置的门诊抢号工具。用户给出的人工路径为：

1. 模拟登录（微信 H5 授权态）
2. 进入「门诊预约」
3. 预约须知 →「是」→「我知道了」
4. 四个院区中优先南部院区，其次高科园区
5. 按科室名称进入指定科室
6. 每日 7:30 放号；医师优先主任医师，其次副主任医师
7. 选可约日期 →「预约」
8. 选时间段 →「确认」
9. 确认就诊人
10. 填写验证码 →「预约」

约束：页面为微信内 H5；号源瞬时竞争；验证码通常需人工介入；站点结构可能随时变更。

## Goals / Non-Goals

**Goals:**

- 以可配置方式完成上述预约闭环（科室、院区优先级、医师职称优先级、就诊人、放号时刻）。
- 先跑通「模拟登录 + 会话复用」，再叠加预约流程与 7:30 调度。
- 关键关键可观测：每一步成功/失败原因可日志追踪，便于页面改版后快速修补选择器或 API。
- 验证码步骤默认人工输入（CLI/本地弹窗），提交前可二次确认。

**Non-Goals:**

- 不做倒号、多账号批量占号、绕过验证码的黑产能力。
- 不实现完整医院 App/小程序其它业务（缴费、报告、医保卡展示等）。
- 首版不承诺 UI 页面（以 CLI/配置驱动为主）；不做分布式多机抢号集群。
- 不保证在医院反爬/风控升级后仍 100% 可用（需保留适配层）。

## Decisions

### 1. 自动化形态：Playwright 浏览器自动化为主，HTTP 为辅

- **选择**：首版用 Playwright（Chromium）驱动微信 H5 同构页面流程，按截图与 DOM 走用户路径；对已识别的稳定 XHR/接口可逐步下沉为直接 HTTP 调用以提速。
- **理由**：齐脉页动态渲染、弹层多（须知、时段、确认、验证码），纯逆向成本高且易碎；浏览器路径与用户描述一致，便于对齐截图验收。
- **备选**：纯 `requests`/`httpx` 逆向 API — 更快但对登录签名、加密参数不透明；留作第二阶段优化。

### 2. 语言与工程布局：Python 包 + YAML 配置

- **选择**：`Python 3.11+`，项目结构大致为：
  - `src/robjy/`：核心库（session、flow、priority、scheduler）
  - `config/example.yaml`：科室、院区优先级、医师职称、就诊人、放号时间
  - `scripts/grab.py`：CLI 入口
  - `tests/`：策略与流程状态机单测（页面交互用 mock）
- **理由**：脚本生态成熟，Playwright Python API 稳定；配置与代码分离便于改科室而不改代码。
- **备选**：Node.js + Playwright — 亦可，但与仓库名/后端工程师习惯相比 Python 更直接。

### 3. 登录策略：会话导出/注入 + 过期重登

- **选择**：支持两种模式：
  1. **手动授权一次**：用户在有头浏览器完成微信扫码/授权后，导出 storage_state（Cookie + localStorage）复用；
  2. **复用已有 state 文件**：无头启动注入 state，探测首页是否仍为登录态（如出现医保卡/姓名），失效则提示重新授权。
- **理由**：微信 OAuth `code` 一次性且与公众号绑定，无法在服务端稳定“静默模拟”完整微信登录；持久化浏览器态是务实首版。
- **备选**：抓包复用 Token — 作为增强，需先抓到稳定字段后再抽象。

### 4. 流程编排：显式状态机

- **选择**：`BookingFlow` 状态机：`AuthReady → Home → Notice → CampusSelect → DeptSelect → DoctorDate → TimeSlot → PatientConfirm → Captcha → Submitted | Failed`。
- 每步封装：进入条件、动作、成功断言、超时与重试次数。
- **理由**：抢号过程易中断（弹层、无号、网络），状态机便于断点续跑与日志对齐用户步骤 1–10。

### 5. 选择策略：可插拔 PriorityPolicy

- **院区顺序**：配置列表，默认 `["南部院区", "高科园区"]`（忽略北部/东部除非配置加入）。
- **医师职称顺序**：默认 `["主任医师", "副主任医师"]`；同职称下可按可约最早日期/最早时段打分。
- **科室**：精确或包含匹配配置中的科室名（如「儿童口腔科」）；先左侧大类（如口腔科）再右侧子科室，以实际 DOM 为准实现适配器。
- **理由**：与用户规则一致且可改配置扩展。

### 6. 放号调度：本地定时 + 放号窗口高频轮询

- **选择**：按配置时区（`Asia/Shanghai`）在 `07:30:00` 前提前 N 秒进入热身（打开科室页、完成须知）；`07:30` 起以短间隔刷新可约日期/号源，直到成功、超时或达最大尝试次数。
- **理由**：放号瞬时；过早刷新无意义，过晚丢失窗口。
- **备选**：系统 cron 调起进程 — 一并支持，调度核心仍在进程内窗口控制。

### 7. 验证码：人工输入通道

- **选择**：检测到验证码图/输入框时，将截图保存到本地并阻塞等待 stdin/本地回调填入；填入后点击「预约」。
- **理由**：首版可靠、合规边界清晰；OCR/打码服务可作为可选插件，默认关闭。

## Risks / Trade-offs

- **[页面/接口改版导致选择器失效]** → 选择器与文案集中到 `adapters/shqmxx/`；关键步骤截图断言；失败日志带 DOM 片段。
- **[微信登录态无法纯无头伪造]** → 明确「半自动登录」；文档说明首次需人工授权。
- **[7:30 竞争与风控限流]** → 控制轮询频率；单账号单进程；失败退避；不做多开刷接口。
- **[验证码延迟导致号源丢失]** → 前置步骤尽量在放号前完成；验证码阶段减少无关操作；可配置「发现号源即通知」以便人更快输入。
- **[合规/ToS]** → README 声明仅限本人就医；默认最终提交需确认开关 `confirm_submit: true`。
- **[Playwright 比纯 API 慢]** → 热身阶段预导航；识别稳定 API 后对「刷号源/锁号」路径做 HTTP 加速（保留浏览器完成复杂弹层）。

## Migration Plan

1. 初始化 Python 项目与依赖锁定（`pyproject.toml` / `requirements.txt`）。
2. 实现 session 登录与首页探测，产出 `storage_state.json` 用法文档。
3. 按状态机逐步接通预约链路（先手动触发，再接 7:30 调度）。
4. 用配置跑通一条「指定科室 + 南部/高科」演练（非放号高峰可测到验证码前）。
5. 放号日小流量验证；失败则回退到人工，同时根据日志修适配器。

回滚：停止调度进程即可；无服务端迁移。配置与 state 文件本地保留。

## Open Questions

1. 目标科室的稳定名称与是否跨院区同名（实现时以配置 + 院区上下文消歧）。
2. 验证码交互偏好：终端输入 vs 简易本地 Web 回调（首版终端，可后续加）。
3. 是否需要成功/失败推送（Server酱、邮件、桌面通知）— 建议二期。
4. 齐脉是否暴露较稳定的 JSON 接口可直接锁号 — 需在联调时抓包确认后再决定是否下沉 HTTP。
